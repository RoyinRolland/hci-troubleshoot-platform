# 被拒候选专家复核处置与仅案例推荐降级门禁

## 结论

「无信号案例可发布为仅案例推荐」与「存在未处理被拒候选时禁止降级」**不是两条冲突的门禁，而是同一条规则的两个分支**：空信号文档只有"干净"（无未处置被拒候选、无孤儿语义画像、生成元数据非异常态）才判 `reference_only` 放行。此前平台缺失的是"干净"的达成路径——专家对被拒候选只有「恢复并编辑」一个动作，**没有任何"复核后放弃"的处置出口**，导致有意降级为纯文本案例推荐的 KBD 死锁。本次为被拒候选补齐专家显式处置能力（复核忽略 / 撤销处置），"不能**自动**降级"的门禁语义保持不变。

## 1. 问题复盘（staging 案例 43596）

- **现象**：专家删光 KBD（support_id 43596，kbd_entry id 2468）全部信号后，审查面板持续显示「有 1 项需要专家处理：关键信号校验失败：无信号案例存在未处理的抽取异常或拒绝候选，请先复核；不能自动降级为案例推荐；请按该原因修正后再保存」。
- **数据状态**：`signals=[]`、无 `semantic_entry_profile`、`generation_metadata.status="manual_reviewed"`，但 `signals_json.rejected_candidates` 残留 3 条 AI 抽取门禁拒绝记录（sig_002 关键字无法从 evidence 逐字追溯、sig_003 `operator:'gte'` 非法、sig_004 缺日志路径 evidence）。
- **判定链**：`validate_kbd_publishable_signals_json`（`backend/shared/schemas/signal_schema.py`）空信号时走 `capability_of` → `is_reference_only`（`backend/shared/schemas/knowledge_capability.py`）→ `rejected_candidates` 非空即 False → 抛出上述门禁错误。
- **死锁成因**：报错要求"请先复核"，但 UI 复核入口只有「恢复并编辑」（复制候选进信号列表，审计快照按设计保留）；全代码库不存在清除/处置 `rejected_candidates` 的端点；逐条删除信号的 `_delete_signal_from_document` 不触碰该字段；重跑抽取会整体重建文档、覆盖专家"删光信号"的意图且这 3 条候选大概率再次被拒。

## 2. 方案

### 2.1 契约层（shared）

- `rejectedCandidate` Schema（`backend/scripts/gen-schemas.py` → `signal.v2.schema.json`）新增可选字段 `expert_dismissal`：`{reviewed_by(1-64), reviewed_at(date-time), note(1-500)}`，三字段全必填、`additionalProperties:false`。处置是**附加审计事实**，候选快照（candidate/reason/reason_code）原样保留。
- 顺带修复既有 bug：`reason_code` enum 补 `tool_restricted`（`extract_signals.py` 的 `REJECT_REASON_CODES` 早已包含，qfk_var 自由文本剥离会写入该码，但 enum 缺失导致此类文档 `validate_signals_json` 必炸）。
- `is_reference_only` 新判定（fail-closed）：`rejected_candidates` 每项都必须是 dict 且带合规 `expert_dismissal`（reviewed_by/reviewed_at/note 全非空）才算"已处置"；任何畸形项、非列表值维持拦截。管道自动忽略仍被禁止——处置只能由专家动作写入。

### 2.2 服务层（kb-service）

- `KbdUpdateRequest` 新增单对象处置分支（镜像 `delete_signal_id` 先例，符合 V-007"单对象动作不夹带无关草稿"）：
  - `dismiss_rejected_candidate_id` + `dismiss_rejected_note`（必填 1-500）+ `reviewer_id`（必填）→ 写入 `expert_dismissal`；
  - `revoke_rejected_candidate_id` → 移除 `expert_dismissal`（误处置回退；重抽取会冲掉专家编辑，不是安全恢复路径，故必须提供撤销）；
  - 与 `signals_json`/`delete_signal_id` 互斥（400）；候选按 `candidate.id` 稳定定位，无匹配 404（`KBD_REJECTED_CANDIDATE_NOT_FOUND`）、重复 422 fail-closed，不提供展示序号兜底（V-003）。
- 工作稿 PATCH 与 maintenance PATCH 双路径均支持；复用既有乐观锁（409 `KBD_EDIT_CONFLICT`）、`_prepare_expert_draft_signals` 复验、KbdRevision 冻结审计。
- 审计三件套：① `expert_dismissal` 落文档；② `change_annotations` 受控原因码 `rejected_candidate_dismissed` / `rejected_candidate_dismissal_revoked`（服务端补齐，进 `kbd_revision.review_metadata`）；③ 结构化日志 `kbd_rejected_candidate_dismissed/_revoked`。身份沿用诚实口径 `identity_status="unverified_body_reviewer_id"`。
- 门禁报错文案：共享 humanizer 新增专属分支，code `KBD_REJECTED_CANDIDATES_UNRESOLVED`，message 给出两条出路（恢复修正 / 复核忽略），附 `action:{type:"review_rejected_candidates"}` 供前端定位；不再落入"请按该原因修正后再保存"的兜底文案。
- api-gateway 零改动（复用已注册的 PATCH `/api/v1/kbd/{id}` 与 `/maintenance`）。

### 2.3 前端（admin）

- 被拒候选面板：未处置项显示「待复核」标签 + 「复核忽略」按钮（对话框必填处置说明，操作人走 `ensureReviewerIdentity`）；已处置项显示「已复核忽略」标签 + 操作人/时间/说明 + 「撤销处置」；多条待处理时提供「全部复核忽略」（统一说明，串行 PATCH，逐条刷新乐观锁）。
- 全部处置且空信号时，面板顶部提示切换为"可按「仅案例推荐」发布"。
- 审查 issue 出现 `review_rejected_candidates` action 时提供「定位并处理」按钮，滚动至被拒候选面板。

## 3. 行为放开面（知情决策）

全部处置后的空信号 KBD 发布为 `reference_only`，将自动进入既有仅案例推荐链路：playbooks 快照 `executable=False / recommendable=True` → 标题/问题描述推荐池 → agent CDD 未定论时的兜底案例推荐；离线编译只收 `executable`，不受影响。对话框与用户手册均明确提示该后果。**重新抽取整体重建 `signals_json`，处置状态被重置**（历史仅存 KbdRevision），属预期语义。
